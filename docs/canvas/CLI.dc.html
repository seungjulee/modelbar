Command line

One binary, two front ends. Every subcommand drives the same state the menu does, so anything scriptable is testable from a terminal — the menubar cannot be driven programmatically.

/Applications/ModelBar.app/Contents/MacOS/ModelBar --cli <command>
Commands
validate
Parse the manifest, list warnings, check every referenced path exists.
status
Backend health, served model, live telemetry, loaded models, committed GB.
monitor
One-shot htop-style snapshot. Takes two samples — %CPU is a delta.
start <model-id>
Free the port, launch, wait for health. Prints the failing log lines if it doesn't come up.
stop <model-id>
SIGTERM, escalating to SIGKILL after the grace period.
context <model-id> <n>
Set the context window used on the next load. Rejects sizes outside the model's ladder.
discover
Models on disk or in a backend's inventory that no manifest entry references.
harness show
What Hermes, Pi, Codex and Claude Code currently point at.
harness set <h> <model|api>
hermes | pi | codex | claude. Registers the model, then moves the pointer — never the other way round.
Flags
--manifest <path>
Use a scratch manifest. Works in GUI mode too, and redirects every config write — including Codex profile files.
--force
Permit an over-budget load. Without it the CLI refuses rather than thrashing into swap.
CLI and app don't share state

The installed app and a directly-run binary use different preference domains (com.sj.modelbar vs ModelBar). A context size set via one is invisible to the other. Prefer the installed path (/Applications/ModelBar.app/…/ModelBar --cli) so the GUI sees what you set.
